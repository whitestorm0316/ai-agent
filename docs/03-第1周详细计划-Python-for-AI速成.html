1.2 配 ruff + mypy，找回编译期检查 约 30min

[tool.ruff]

[tool.ruff.lint]

2.3 Pydantic（75min）—— 本周最重要的知识块 约 1.25h

Pydantic 在 AI 生态里的地位 ≈ Go 的 struct tag + 校验库。更重要的是——它直接决定了 LLM 的 tool schema 和 structured output 怎么写。第 2 周你会用到它两次。

# src/tools.py
from pydantic import BaseModel, Field

class WeatherArgs(BaseModel):
    """查询指定城市的当前天气。"""
    city: str = Field(description="城市名称，例如：深圳")
    unit: str = Field(default="celsius", description="温度单位，celsius 或 fahrenheit")

print(WeatherArgs.model_json_schema())

输出（这就是 OpenAI function calling 要的格式，第 2 周直接喂给模型）：

{
  "properties": {
    "city": {"description": "城市名称，例如：深圳", "title": "City", "type": "string"},
    "unit": {"default": "celsius", "description": "温度单位，celsius 或 fahrenheit",
             "title": "Unit", "type": "string"}
  },
  "required": ["city"],
  "title": "WeatherArgs",
  "type": "object"
}
划重点：Field(description=...) 里的文字会直接变成模型看到的工具参数说明。写得好，工具调用准确率就高；写得含糊，模型就乱调。这是很多人忽略的细节，也是第 7 周「工具调用成功率」优化的起点。
Session 2 验收：能解释 model_json_schema() 输出里每一层是什么；能说出为什么 Pydantic 在 AI 生态里是核心组件；能独立写出一个带嵌套模型和默认值的 Schema。

4Session 3 · asyncio 心智模型（2.5h）本周最关键

这一节比语法重要十倍。写错语法只是报错，写错并发模型是线上事故。

3.1 先纠正直觉：asyncio 不是「更轻的线程」 45min
维度Go goroutinePython asyncio 协程
调度方式抢占式，运行时自动切换协作式，只在 await 处切换
并行能力真并行，吃满多核单线程，同一时刻只有一个协程在跑
阻塞影响一个 goroutine 阻塞不影响别人任何同步阻塞会卡死整个事件循环
数量级百万级 goroutine 没问题协程也轻，但阻塞一个就全停
一句话记住：asyncio 不是「更轻的线程」，而是「一个线程 + 一个事件循环 + 一堆可以暂停的函数」。所有协程共享同一个线程，谁阻塞谁就是全队的罪人。
3.2 核心 API 对照 45min
GoPython asyncio用途
go func(){}asyncio.create_task(coro)起一个并发任务（必须持有返回值的引用）
errgroup.Groupasyncio.gather(*coros)并发聚合并等全部完成
errgroup + 错误传播asyncio.TaskGroup()3.11+ 更安全的并发（失败自动取消兄弟任务）
context.WithTimeoutasyncio.wait_for(coro, timeout)超时控制
sync.Mutexasyncio.Lock()保护临界区
带缓冲 channel 限流asyncio.Semaphore(n)限制并发数
defer cancel()async with 块资源自动释放
3.3 踩坑实验：亲手制造一次事故 约 1h

实验 A —— 在 async 函数里写同步阻塞：

import asyncio, time

async def task(i: int) -> int:
    time.sleep(3)              # ❌ 同步阻塞，整个事件循环停摆
    return i

async def main() -> None:
    start = time.perf_counter()
    await asyncio.gather(*(task(i) for i in range(5)))
    print(f"耗时 {time.perf_counter() - start:.1f}s")   # 会是 ~15s，不是 3s

asyncio.run(main())

实验 B —— 只改一行，性能差 5 倍：

async def task(i: int) -> int:
    await asyncio.sleep(3)     # ✅ 让出控制权，其他协程可以跑
    return i
# 耗时 ~3s

实验 C / D —— 把同样的逻辑换成真实 HTTP 请求，分别用同步 requests 和异步 httpx.AsyncClient，对比耗时。结论会完全一样。

这四个实验做完，你这辈子都不会在 async 函数里写同步阻塞调用了。比看十篇文章有用。第 4 周的 Agent 项目、第 7 周的并发服务，全都建立在这次理解之上。
Session 3 验收：能画出事件循环执行 3 个协程的时序图；能列出一份「哪些操作会阻塞事件循环」的清单；能用 Semaphore 写出并发限流为 5 的代码。

5Session 4 · 实战：并发调用大模型 API（4h）

本周的核心交付物。做完这个，你就有了第 2 周 Function Calling 的代码基础。

4.1 写一个带超时和限流的并发调用器 约 2.5h 
# src/concurrent_llm.py
import asyncio, os, time
import httpx

URL = "https://api.deepseek.com/chat/completions"
HEADERS = {"Authorization": f"Bearer {os.environ['DEEPSEEK_API_KEY']}"}
PROMPT = "用一句话解释什么是 AI Agent"

async def one(client: httpx.AsyncClient, i: int) -> str:
    resp = await client.post(
        URL, headers=HEADERS,
        json={"model": "deepseek-chat",
              "messages": [{"role": "user", "content": PROMPT}]},
    )
    resp.raise_for_status()
    return resp.json()["choices"][0]["message"]["content"]

async def main() -> None:
    limits = httpx.Limits(max_connections=5, max_keepalive_connections=5)
    async with httpx.AsyncClient(timeout=30.0, limits=limits) as client:
        start = time.perf_counter()
        results = await asyncio.gather(
            *(one(client, i) for i in range(10)),
            return_exceptions=True,        # 单个失败不拖垮整批
        )
        print(f"并发耗时 {time.perf_counter() - start:.1f}s")
        for r in results:
            print("ERR" if isinstance(r, Exception) else "OK")

asyncio.run(main())
4.2 三组对比实验 + 记录数据 约 1h
  • 串行版：for 循环调 10 次，记录总耗时
  • 全并发版：asyncio.gather 不限流，记录总耗时
  • 限流版：加 asyncio.Semaphore(3)，记录总耗时
  • 同时记录每次调用的 token 消耗，算出这一轮实验的总成本

做成一张表存进项目 README.md——这是你第一份「量化数据」，后面面试要讲的就是这个习惯。

限流的写法（记住 async with 这个模式）： 
sem = asyncio.Semaphore(3)

async def limited(client: httpx.AsyncClient, i: int) -> str:
    async with sem:                    # 超过 3 个就排队等
        return await one(client, i)
4.3 加测试：验证「单个失败不影响整批」 约 30min

  • 测试 1：正常路径，10 个请求全部返回 OK
  • 测试 2：故意让其中 1 个请求超时（或传错 URL），验证其余 9 个仍正常返回
Session 4 验收：有一份串行 vs 并发 vs 限流的耗时对比数据；用异常注入验证过「单个失败不影响整批」；能说清 Semaphore 限流和 httpx.Limits 连接池的区别（前者控制业务并发度，后者控制底层连接数）。

8本周最容易踩的 7 个坑

坑后果正确做法
在 async 函数里用 requests / time.sleep服务直接串行化，并发能力归零只用异步库：httpx.AsyncClient / asyncio.sleep
asyncio.create_task() 后不保存返回值任务可能被 GC 回收，静默消失存进变量或集合，或用 TaskGroup
忘记写 await不报错，但函数根本没执行mypy 能查出部分；养成习惯
